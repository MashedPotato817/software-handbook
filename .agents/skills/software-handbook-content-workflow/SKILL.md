# 手册内容贡献工作流

将编写目标和已有材料整理为可审阅的中文手册草稿。默认完成内容、来源、验证状态和导航检查；实际安装验证与提交发布按会话已有授权执行。

## 定位本次内容

先阅读仓库 [协作约定](../../../AGENTS.md)、[贡献说明](../../../CONTRIBUTING.md)、[README](../../../README.md)，再查看相关工具页面与根首页。格式、分类和内容要求以这些文件的当前版本为准。

- **新增工具**：确认工具身份、本篇目标、适用环境与读者已有条件，查看是否已有同名或同用途页面。
- **补充章节**：先读完整原页，定位要补的内容和受影响步骤，沿用现有术语、标题层级及验证说明。
- **整理材料**：核对原稿、截图和链接分别能证明什么，保留来源及署名。截图无法辨认、材料互相矛盾时，只询问影响编写的关键缺口。

只有工具名称和目标时，可以主动检索官方资料并起草。已有条件足以确定路径时直接推进；软件身份、系统环境、版本差异或目标不明会改变步骤时，先问清相关项，再写依赖这些答案的内容。

开始编辑前说明拟改文件与原因。按 [Git 工作流技能](../software-handbook-git-workflow/SKILL.md) 核对仓库状态、选择工作分支并保护无关改动；本技能不另行定义 Git 规则。

## 核对资料与验证边界

优先核对产品官方安装、配置和使用资料，实际打开与本次步骤有关的来源。下载链接、系统条件、版本和选项以查到的资料为依据；学习材料按贡献说明选用，注明出处。

用户提供的原稿和截图可用于整理步骤，但不能单独证明流程已经验证。对“已安装成功”等声明，确认是谁在什么环境、何时验证了哪些步骤，以及实际结果；缺少记录时如实保留待确认项。安装成功不自动证明升级、卸载或其他新增章节已验证。

默认授权是写稿，不据此安装软件、修改用户工具配置或宣称实测成功。需要实际操作验证时，先确认相关授权是否已在会话中给出；有授权则按其范围执行，分别记录文档检查、构建结果与软件操作结果。

## 编写或补充草稿

每个工具的完整手册放在 `pages/<工具或平台>/index.md`。新增工具填写 YAML `title` 与三大类之一的 `category`；既有工具直接补原页，用二、三级标题组织章节。

按贡献说明的试写结构组织内容，并根据本篇目标调整篇幅。对每条操作写清前置条件、可执行步骤、必要选项和预期结果。仅补某个章节时，更新其上下文与关联步骤，不重新生成整篇无关内容。

- 引用与具体步骤相关的来源；来源未支持、也无实际记录的结论标为待确认，不能补造参数、结果或截图。
- 互斥方案分开写选择条件与验证条件，读者只需完成自己采用的路径及公共检查。
- 保留原有有效内容、作者署名和验证记录；新增的未实测步骤单独标注，不把整篇统一升级为“已验证”。
- 有真实截图时核对它与步骤、版本的对应关系；截图缺失可明确标为待补，不伪造画面。

新增工具时，在根首页对应分类维护一个工具链接，教程范围用普通文字说明。补现有章节时，只更新确实受影响的首页或 README 状态。侧栏由页面元数据生成，普通内容贡献无需修改布局或新增依赖、自动化。

## 校验并交付

检查本次改动的相对链接、锚点、图片路径、YAML 头部、标题层级及首页单一入口；运行 `git diff --check`，新增文件也要实际读取检查。保留正文、来源和验证状态之间的一致性。

使用仓库当前具备的方式核对渲染。已有构建环境时运行适用构建并查看页面与导航；环境缺失时先完成可做的静态检查，明确渲染未验证，不为此默认安装新依赖。检查通过不等于软件安装或使用成功。

交付说明包含：改了哪些文件、内容目标与来源、已执行检查及结果、待人工验证或待补资料、推荐的下一步 Git 操作。默认到本地可审阅草稿为止。

若用户已授权提交、推送或 PR，衔接 Git 工作流技能执行对应步骤，不重复索要已有授权。PR 说明仍需目的、来源、验证与待确认事项；未定稿内容使用 Draft PR，合并与发布按明确授权执行。

## 调用示例

`使用 $software-handbook-content-workflow，为 VS Code 新增 Windows 安装与首次运行草稿。可查官方资料，先不安装软件或提交。`
